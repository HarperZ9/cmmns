Daylight Commons privacy policy

Updated 2026-10-23.

Daylight Commons runs entirely in your browser. It has no server, no account, no analytics and no telemetry. Nothing Daylight Commons reads or works out is sent to the author. Apart from the site you are on, two features make requests, each off by default and only after you turn it on and click: Other coverage requests the public news feeds of outlets you choose and sends nothing from the page; evidence lookups send the repository names and web domains a post links to GitHub, rdap.org and the Internet Archive. Both are described below.

What Daylight Commons reads

Daylight Commons reads what the site you are on has already shown or loaded for you: the replies on the page, the account details the site discloses (for example X's "About this account" label), and the post data the site's own app downloaded. It reads nothing the site does not show its viewers, and never reads IP addresses.

Requests Daylight Commons makes

Daylight Commons sends no data to the author, to analytics services or to any server of its own. It makes these requests, all to the site you are already using, with that site's own session in your browser:

On Bluesky, Threads, TikTok and Mastodon servers Daylight Commons makes no request at all: it reads the page and copies responses the site's own app already loaded (on TikTok and Mastodon, the comment and thread lists; Daylight Commons never reads request headers or login tokens).

Mastodon servers. Daylight Commons has no access to any Mastodon server until you turn it on for that server. When you open Daylight Commons' toolbar button on a page Daylight Commons does not run on, it checks two things on that page only: whether it is the Mastodon web app, and the app's version and domain. If it is, the button offers "Turn on Daylight Commons here", and your browser asks you to allow access to that one server. The list of servers you turned on is kept in pb.instances.v1; Options, Mastodon servers, Remove takes the access back.

Fact-check matching runs against a table bundled inside Daylight Commons, so post text is never sent to a fact-checking service. Site cards (owner, owner type, founding date, country, state links and a site's fact-check record) come from tables bundled inside Daylight Commons too, on links, on search results when you turn an engine on, and on the page you are reading when you press "Site card for this page". None of these send anything.

Evidence lookups (off by default)

Evidence lookups are off until you allow them, either from the first "Look up evidence" click under a launch campaign section or in the options page. Each lookup is one click, for the post you are viewing. Daylight Commons sends the repository names (owner/repo) and web domains that post links to, and nothing else: not the post's text, not your account, not anyone's handle. They go to GitHub's API (api.github.com), to rdap.org, which forwards to the registry for the domain, and to the Internet Archive (web.archive.org). Each receives the request like any web request, so it sees your IP address and the time. Requests carry no cookies. If you add your own GitHub token in the options page, it is kept in this browser and sent only to api.github.com, to read star timestamps. Daylight Commons does not query ad libraries; it gives you links to open yourself. "Save this post to the Internet Archive" opens the archive's own save page in a tab, and the archive then sees which post you asked it to save. Results are kept as sealed receipts in this browser (pb.seal.v1) until you clear Daylight Commons data.

Other coverage (off by default)

Other coverage is off unless you turn it on in the options page. When it is on, you choose which outlets to ask from a suggested list, and you may add any RSS or Atom feed address. Choosing an outlet asks the browser for access to that one feed's host, never to all sites. When you click "Find other coverage" on an article's site card, Daylight Commons requests each chosen outlet's feed from the feed's own address, then compares the article's title with the feed's headlines on your device.

Daylight Commons sends nothing from the page: not the title, not the page address, not your history, not any post, not any account. Each request is an ordinary download of a public feed, with no cookies, no referrer and no header added by Daylight Commons, and Daylight Commons does not follow a redirect to another address. Each outlet receives the request like any web request, so it sees your IP address, the time and your browser's standard headers, and could guess that someone was reading news at that moment. No aggregator or Daylight Commons server is involved. Answers are kept in memory for ten minutes and never stored. Before the first request the card lists every host it will ask and waits for your click; adding an outlet resets that consent. Turning the option off withdraws every feed host's permission and forgets your choices.

Daylight Commons 2.x used the GDELT Project's search service for this feature, which received the main words of the title. Daylight Commons 3.0 removed it and gives back that permission on update.

The window offers reverse image search links (Google Lens, TinEye, Bing, Yandex) for media. Those open only when you click one, and then that service receives the image address.

Media checks, only when you click. "Check this file" re-requests one image or video file the page already loaded, from the exact address the page used (for X, its own media server), without cookies, so the browser usually answers from its cache. Daylight Commons reads the file's Content Credentials and metadata in the tab and keeps the result in memory only. "Take 4 frames" copies frames from the page's own video player in the tab; choosing a search service then copies one frame to your clipboard and opens that service, which receives nothing until you paste the frame there. Credentials stored online (a file that points to a remote manifest) are never fetched.

Reading text in an image, off by default, only when you click. With "Read text in images" turned on in the options page, "Read text in this image" re-requests that one image the same way, from the address the page used and without cookies, and hands its bytes to Daylight Commons' own background worker in your browser. The words are read there by code and weights shipped inside Daylight Commons; nothing is downloaded for it. The image, the text and any hash of either never leave your browser. The text is kept in memory for that window only.

Everything is kept in chrome.storage.local (Firefox: browser.storage.local) in the browser profile you installed Daylight Commons in. It is not synced to other devices.

Carrier-safe evidence bundles

An ordinary bundle is signed with this browser's own key, so every bundle you save carries the same key id, and it records the exact save time and the page address. Anyone who holds two of your bundles can tell they came from one install. For a bundle you will hand to someone else, tick Carrier-safe on the card page, or use radar analyze --carrier-safe on the command line:

  • it is signed with a one-time key made for that bundle alone, which is never stored and is gone when the signing ends;
  • it keeps the day it was saved and no time of day, and blanks every time of day inside it;
  • it leaves out the page address unless you type one in;
  • it names the tool by its major version only.

Its signature proves the bundle is unchanged and says nothing about who made it. The profile cannot hide two bundles sent from one connection: whoever sees the network can still link them. It strips nothing from your own files, and the post ids it carries identify the thread and, on X, when each post was made. If you hold information that could put you at risk, do not send it through Daylight Commons: use a newsroom's SecureDrop or a GlobaLeaks site through Tor Browser, and their own tools for removing hidden data. The profile has had no independent review.

Your controls

  • Options page: switch Daylight Commons off per site or pause it everywhere, change how long it keeps data, and press "Clear all Daylight Commons data", then confirm, to delete everything above except your choices: your settings, the Mastodon servers you turned on, your data packs and the keys you trust, and the tour's "No more tips". The bundle signing key stays too, so bundles you already shared still check as yours.
  • History page: clear the history, connections and trails on their own.
  • Save report: writes a JSON file to your computer only when you click it. It holds the thread report, account labels and flags, and leaves reply text out.
  • Save feedback to a file (options page): writes your marks to a JSON file on your computer only when you click it. Daylight Commons never sends it. You choose whether to share it, for example by attaching it to an issue on Daylight Commons' repository. "Clear feedback" deletes your marks.
  • Analyse a file: reads a saved page, thread JSON, a platform data export or a media file you choose, on your device. The file is not kept and nothing is sent.
  • Save signed bundle (Analyse a file and the thread card page): writes a JSON file to your computer only when you click it. It holds post ids, the evidence with the matched words, Daylight Commons' version, a hash of its data tables, the time and your bundle key's public half. Full post text goes in only if you tick the box. Daylight Commons never sends it.
  • Removing Daylight Commons deletes everything it kept.

What Daylight Commons never does

  • Sends anything to the author, or to a third party except what evidence lookups send when you turn them on and click: the repository names and web domains a post links to.
  • Sells, shares or uses data for advertising.
  • Guesses who runs an account, or anyone's age, gender, ethnicity, religion or politics.
  • Links accounts across sites.

Changes

Changes to this policy are listed in Daylight Commons' changelog with the version that made them.
