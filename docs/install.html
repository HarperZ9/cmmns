Install Daylight Commons

Download a release, check it, install it in Chrome, Edge, Brave or Firefox, and rebuild it from source.

How it works Install Privacy How it is measured Catalogue Source

Updated 2026-10-23.

Every Daylight Commons release can be downloaded, checked and installed without a browser store, and its source can be rebuilt without any code host. This page says how, and says plainly where a browser maker still stands in the way.

What a release holds

  • radar-chrome-<version>.zip: the Chrome, Edge and Brave build.
  • radar-firefox-<version>.xpi: the Firefox build sent to Mozilla's add-on store.
  • radar-firefox-self-<version>.xpi: the Firefox build for installing from this site once Mozilla has signed it. It checks this site for updates.
  • radar-cli-<version>.zip: the command line tool. Unzip it anywhere and run node bin/radar.mjs verify <file> with Node 22 or later to check a signed evidence bundle or a saved evidence chain offline. No install step.
  • FILES-<version>.sha256: the hash of every file inside each package.
  • radar-<version>.bundle: the whole source history at the release commit, as one git file. Commits before 3.0.0 also hold the Conso font, under its designer's licence; 3.0.0 and later ship only fonts under the SIL Open Font License.
  • SOURCE: the commit and the Node version the release was built with.
  • release-key.json: Daylight Commons' public signing key.
  • SHA256SUMS and SHA256SUMS.sig: the hash of every file above, and Daylight Commons' signature over that list.
  • verify-offline.html, KEY-CARD.html and KIT-GUIDE.txt, from 3.2.0: the offline kit's checker, a printable key card with a QR copy of the key id, and plain guidance for use without the internet. SHA256SUMS covers them like every other file.
  • HEAD.json and HEAD.sig, from 3.2.0: the signed head. It names SHA256SUMS and the catalogue by hash, with a version number that only goes up, the time it was signed and a date it expires, 90 days after the release commit.

Check a download

Daylight Commons signs SHA256SUMS with its project key, an ECDSA P-256 key whose private half never enters the repository or any server. The key id is:

0e5e 1984 0565 840c 977e 0f03 6c9a c021

Compare that id with one you got another way: this site, the repository's docs/release-key.json, a mirror, or a person you trust. A key that arrives in the same download as the files proves nothing on its own.

The signed head stops an old release from passing as the current one. Each device keeps the highest head version it has accepted. A lower version, a different head under the same version, or a release with no head after one with a head, is refused, and the refusal names the rule in one sentence. A head past its expiry still verifies and is marked Expired: Daylight Commons keeps working and says "Catalogue dated 2026-10-22. Newer campaigns may be missing." The expiry is the signer's claim. A device with a wrong clock uses the latest signed time it has seen.

In the extension, the options page has Check a signed head: pick HEAD.json and HEAD.sig. The account card and the toolbar popup then show the catalogue date, when the head was last seen, its expiry and how many signatures it carried, as Current, Aging (head older than 30 days) or Expired. Releases today carry one signature, and the line says "single-signer release".

To check in this browser, use the checker at the end of this page. It runs on your device and sends nothing. To check with Node 22 from a copy of the source, run node scripts/verify-release.mjs <folder>; it checks the head first, then prints the key id, checks the signature, then every file's hash, then the bundle. It keeps the highest head version in ~/.radar/head-state.json; add --no-state to look at an old release on purpose.

Check a kit with no network

A release folder is also an offline kit. Copy the whole folder to a USB stick or SD card and hand it over. The person receiving it needs a browser and nothing else:

1. Open verify-offline.html from the kit. It works from the stick with the network off. The project key is built into the file; it fetches nothing, loads no script or font from anywhere, and sends nothing. 2. Compare the key it shows with the printed KEY-CARD.html, or better, a card or key id from a second source. If they differ, stop. 3. Pick the kit folder, or every file in it. The page checks the signed head, the signature over SHA256SUMS and every file's hash. It names any file that changed, any file the signature does not cover, and the key it found when the kit was signed by another key. 4. Install only when it says "Kit verified".

The page keeps no record between visits, so it cannot refuse an older kit on its own. It shows the release, the head version and the expiry; compare them with the newest you have seen. KIT-GUIDE.txt says the same in plain language. It is a draft that a security partner has not reviewed yet.

The same page checks one signed evidence bundle with no network: pick it under "Or check one evidence bundle". The page is also published beside this one as verify-offline.html. To make a kit folder from a release folder with Node, run node scripts/kit.mjs <release folder> --out <kit folder>.

Rebuild it yourself

The packages are reproducible: entries sorted, fixed timestamps, no extra fields. From the bundle:

  • git clone radar-<version>.bundle radar
  • cd radar and npm run ci to run every check the project runs on GitHub, with no network.
  • npm run package, then compare dist/SHA256SUMS with the release.

The same commit gives the same bytes on the same zlib build. A different zlib can compress differently; the per-file list in FILES-<version>.sha256 does not depend on zlib, so compare that when the package hashes differ.

Install in Chrome, Edge or Brave

Chrome installs extensions from outside the Chrome Web Store only in two ways, both set by Google:

  • Developer mode. Unzip the package, open chrome://extensions, turn on Developer mode, press Load unpacked and pick the folder. Chrome may show a warning about developer-mode extensions, and this copy does not update itself: install each new release the same way.
  • Enterprise policy. A managed computer can force-install Daylight Commons from a self-hosted address with the ExtensionInstallForcelist policy. This needs an administrator.

There is no other way around the store for an ordinary Chrome install. That is Google's rule, and Daylight Commons cannot change it.

Install in Firefox

Release versions of Firefox install only add-ons that Mozilla has signed, even when the file comes from somewhere other than Mozilla's store. Mozilla signs radar-firefox-self without listing it in its store; once signed, open the file in Firefox to install it, and Firefox checks firefox/updates.json on this site for new versions.

No release so far carries a Mozilla-signed file, 3.6.0 included, and firefox/updates.json is not published yet. Until Mozilla signs the self-distributed build or lists Daylight Commons on Firefox Add-ons, release Firefox can load it only for one session: open about:debugging, choose This Firefox, then Load Temporary Add-on, and pick the .xpi. Firefox Developer Edition, Nightly and unbranded builds can turn signing checks off.

That signature is Mozilla's requirement. Daylight Commons cannot remove it, and a Mozilla signature says only that Mozilla's automated review passed.

If the code host goes away

Daylight Commons' source is hosted on GitHub today. Each release's bundle holds the whole history, so the project survives without it: clone the bundle, then push it to any git host. Any mirror that serves the same bundle and the same signed SHA256SUMS is as good as the original, because the signature is what you check, wherever the files came from. node scripts/mirror-check.mjs <url>... compares mirrors: it names a mirror that is unreachable, serves an older head, serves a different head under the same version, or serves a file whose bytes differ from the signed list.

What this does not prove

A valid signature shows the files were signed by the holder of Daylight Commons' key and have not changed since. A valid head shows the signer chose these files at that time. It does not show the files are safe. The offline checker cannot show its own key is right if the kit came from an attacker: the printed card and a second source are the defence. The kit and its checker have had no independent security audit. It does not show who holds the key, that the key was never stolen, or that the code is safe. A reproducible build shows the package came from the published source; it does not show the source is free of mistakes. Read the source, or ask someone you trust who has.
